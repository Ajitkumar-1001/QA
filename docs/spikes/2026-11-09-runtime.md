# Runtime feasibility spike (2026-11-09)

- **Status:** reviewed. One Goldfish round was run by three isolated reviewers (design, implementation readiness, zoom-out), and its 13 fixes are applied here.
- **Evidence:** the probe scripts and sourced doc answers (with the critic's corrections) are in [2026-11-09-evidence/](2026-11-09-evidence/). The scripts are throwaway, and none of their code is reused in the app.

## Question

Can a Mastra agent drive a real browser in an isolated sandbox on Vercel Hobby, given that a Hobby function runs for at most 300s?

## Answer

**Plausible.** Each piece works on its own:
- the sandbox boots;
- Chromium runs inside the sandbox;
- a Mastra workflow resumes across processes from Postgres.

**The integrated run is unproven:** a Mastra agent driving that browser, on production. Proving it is milestone 0 (see the [acceptance checks](#acceptance-checks-for-the-walking-skeleton)).

## Documented limits

Fetched 2026-11-09 and re-checked by a second agent.

- **Hobby functions:** at most 300s with Fluid compute (that is also the default), 2 GB / 1 vCPU. `after()` and `waitUntil` share the 300s. Sources: vercel.com/docs/fluid-compute, /docs/limits.
- **Sandbox quota on Hobby:**
  - Free within the monthly quota: 5 h active CPU, 420 GB-h memory, 5,000 creations, 20 GB data transfer.
  - Over quota, creation is **blocked, not billed**. The docs give the reset two ways: "next billing cycle" or "30 days after first use".
  - Limits: 45 min per session, 10 concurrent sandboxes, 4 vCPU at most.
  - Source: /docs/sandbox/pricing.
- **Exposed sandbox ports** are public URLs with no authentication. Source: /docs/sandbox/concepts.
- **Egress firewall:** offers `deny-all`, SNI domain allow-lists (TLS only) and subnet allow/deny rules. Plain HTTP can be filtered by IP only. `subnets.allow` bypasses SNI filtering. Source: /docs/sandbox/concepts/firewall.
- **Scheduling on Hobby:**
  - Cron runs at most once a day.
  - Queues have the first 1M operations included (behaviour beyond that is undocumented).
  - Workflow DevKit gives 50k events a month, and each step is capped at 300s.
  - Sources: /docs/cron-jobs/usage-and-pricing, /docs/queues/pricing, /docs/workflows/pricing.
- **Hobby terms:** non-commercial personal use only. Commercial use means financial gain for anyone involved. Source: /docs/limits/fair-use-guidelines.
- **Mastra per-call controls:** `maxSteps` (default 5), `stopWhen`, `activeTools`, `toolChoice`, `abortSignal`, and `modelSettings.timeout {totalMs, stepMs}`, which raises `MastraTimeoutError`. Source: mastra.ai/reference/agents/generate.
- **Mastra on Vercel:** `server.timeout` defaults to 180s, separately from `maxDuration`. On serverless, traces need an awaited `flush()`. Traces can persist to Postgres via `MastraStorageExporter`. Sources: mastra.ai/integrations/deploy/vercel, /docs/observability.
- **`@mastra/vercel` sandbox provider:** exposes only the deprecated AL2023 `runtime`. Use `@vercel/sandbox` (v3 or later, for the Ubuntu images) directly.
- **agent-browser** (vercel-labs) is Vercel's documented way to run a browser in Sandbox. It is a persistent daemon that provides:
  - accessibility snapshots with element refs;
  - click, fill and screenshot;
  - console and network inspection;
  - restore from a snapshot.
  Source: agent-browser.dev, vercel.com/changelog/give-your-eve-agent-a-browser.

## Recommendation

**Status:** provisional for brief decisions 1 (where the loop runs) and 2 (browser host), until the walking skeleton passes. Decision 10 (model, step budget, token ceiling) stays **open**, because no model call was made.

**This design assumes Hobby (brief decision 3, the owner's call).** On Pro the overage is billed and needs a spend cap, functions get 800s, and cron runs every minute. The single-invocation shape still holds on Pro.

1. **Loop location (decision 1): one run is one function invocation.**
   - **Trigger:** the run form enqueues a message on a Vercel Queue. The run never executes inside the user's request.
   - **Claim:** the queue consumer claims the run row in one SQL statement (`queued → running`, with a lease deadline). A duplicate delivery that loses the claim is dropped.
   - **Limits on the agent loop:** `maxSteps` ≤ N, `modelSettings.timeout.totalMs` = 240s plus a per-call `stepMs`, and an `activeTools` allowlist. If the deadline hits, the run ends **INCONCLUSIVE**.
   - **Mastra settings:** Mastra runs inside the route handler, with no Mastra deployer, so its 180s `server.timeout` does not apply. Traces are flushed with `await flush()` before returning.
   - **Reserve:** suspend/resume, proven by probe C, is not used in milestone 0. The run is split across invocations only if the skeleton measures that N steps do not fit in 240s. In that case exactly one durability engine is chosen.
2. **Browser host (decision 2): an agent-browser daemon in one sandbox per run.**
   - **Sandbox:** `persistent: false`, with `timeout` = run deadline + 60s and no extension. It is stopped in `finally`.
   - **Daemon:** owns page state and buffers console and network events.
   - **Ports:** none exposed, and the daemon's control channel cannot be reached from page JavaScript.
   - **Tools:** each Mastra tool calls a fixed binary as an argv array (`runCommand(cmd, args)`, never `bash -c`), with arguments validated by a Zod schema on the host. No model text reaches a shell.
   - **Fallback:** first confirm that agent-browser runs on the Ubuntu image. If it doesn't, accept the AL2023 `runtime`.
3. **Lifecycle:**
   - Global concurrency cap ≤ 8, below Hobby's 10.
   - A reaper stops any sandbox whose run lease has expired.
   - A sandbox that dies mid-run makes the run INCONCLUSIVE.
4. **Budget:**
   - Measured so far: one navigation used 49s of CPU, mostly install.
   - The skeleton measures CPU, GB-h and data transfer per N-step run.
   - The app enforces its own monthly run cap below every Sandbox quota and refuses new runs with a clear message, so the platform block is never hit.
   - A baked snapshot or image is **deferred** until a measured limit needs it.
5. **Egress:**
   - **Policy at creation:** deny `10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `100.64/10`, `0/8`, `::1`, `fc00::/7` and `fe80::/10`.
   - **Why not an allow-list:** allowing only the target domain was rejected because it breaks third-party assets (CDNs, fonts), so QA would see a broken site.
   - **Division of work:** the host check validates the submitted URL, and the in-VM policy guards redirects and subresources. "Pin the connection to the validated IP" cannot apply to a browser that resolves DNS inside the VM.

### Alternatives weighed

| Option | Verdict | Reason |
|---|---|---|
| Split every agent step into its own invocation (Mastra suspend/resume) | Rejected for milestone 0 | Rebuilds the agent loop by hand and needs a trigger, idempotent re-entry and a VM kept alive. That was only necessary while Chromium ran inside the function. |
| Workflow DevKit *and* Mastra snapshots | Rejected | Two engines would both own run state. If a split is ever needed, pick one. |
| Cron, or `after()`, as the trigger | Rejected | Cron runs daily only. `after()` is best-effort and shares the 300s. |
| Custom Playwright action scripts | Rejected | Short-lived scripts lose page state and events between calls. The daemon already solves this. |
| Exposed `run-server` or CDP port, driven from the host | Rejected | The port is a public URL with no authentication (probe B worked, but anyone holding the URL could drive the browser). |
| `@mastra/vercel` sandbox provider | Rejected | Deprecated AL2023 runtime only. |
| agent-browser under the Mastra harness | **Chosen** | It is a browser driver, not an agent. Budget, allowlist and timeouts stay in Mastra. |

## Open for the skeleton spec

- Postgres provider. Dev and prod are separate databases.
- PostgresStore or PostgresStoreVNext.
- A fixed acceptance URL and objective.
- How a plain-English objective becomes a checked assertion.
- The run row schema and status set, defined once in one module.
- The trace event schema, and the link from trace to run (store the `traceId` on the run row).

## Acceptance checks for the walking skeleton

1. A run of N = 5 agent steps completes **on production** in under 240s. Cold start and the time for each step are recorded.
2. The sandbox is created through `@vercel/sandbox` (version pinned, v3 or later) from the deployed function, authenticated with the project's OIDC token.
3. Page state, plus console and network capture, persist across all tool calls in the run.
4. Two concurrent queue deliveries of one run produce exactly one execution.
5. From inside the sandbox, the metadata address and every denied range are unreachable over IPv4 and IPv6.
6. Tokens per step are recorded. This sets decision 10.
7. The result and the trace are stored, and the trace is linked to the run.
